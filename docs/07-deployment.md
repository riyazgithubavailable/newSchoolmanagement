# 07 — Deployment (Render + MongoDB Atlas)

Three things go live, each on its own address:

| Service | Project | Example address |
|---|---|---|
| API | `backend/` | `https://instituteos-api.onrender.com` (later `api.yourdomain.com`) |
| School web app | `frontend/` | `https://instituteos-web.onrender.com` (later `app.yourdomain.com`) |
| Platform Admin | `platform-admin/` | `https://instituteos-platform.onrender.com` (later `admin.yourdomain.com`) |

`render.yaml` in the repository root describes all three, so Render can create them in one go.

## 1. Production database (MongoDB Atlas)
Never use the development database (`school_dev`) for real schools.

1. Create a **separate project / cluster** for production (e.g. `school-prod`).
2. **Database Access → Add New Database User**: one user only for the server (e.g. `api_server`), strong password.
3. **Network Access → Add IP Address → `0.0.0.0/0`**. Render's free and starter plans have no fixed outgoing IP,
   so the strong database password is the protection here. (Paid plans with static IPs can be restricted.)
4. **Connect → Drivers** → copy the connection string. Database name: `school_prod`.
5. Turn on **backups** (Atlas → Backup) before real data arrives (needs a paid cluster tier).

## 2. Create the services on Render
1. Push the code to GitHub (branch `main`).
2. render.com → **New → Blueprint** → choose the `newSchoolmanagement` repository. Render reads `render.yaml`
   and shows three services.
3. Fill in the values Render asks for:

| Service | Variable | Value |
|---|---|---|
| instituteos-api | `MONGODB_URI` | production Atlas connection string |
| instituteos-api | `CORS_ORIGIN` | `https://instituteos-web.onrender.com,https://instituteos-platform.onrender.com` |
| instituteos-api | `WEB_APP_URL` | `https://instituteos-web.onrender.com` |
| instituteos-api | `PLATFORM_ALLOWED_IPS` | optional — your office/home IPs, comma separated; leave empty to allow any |
| instituteos-api | `MAIL_FROM`, `SMTP_HOST`, `SMTP_USER`, `SMTP_PASS` | email account for password-reset mails (can be added later) |
| instituteos-web | `VITE_API_URL` | `https://instituteos-api.onrender.com/api/v1` |
| instituteos-platform | `VITE_API_URL` | `https://instituteos-api.onrender.com/api/v1` |

`JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET` and `ENCRYPTION_KEY` are generated by Render automatically.
**Never change `ENCRYPTION_KEY` after going live** — existing 2-step verification secrets would stop working
(every platform owner would need `reset-2fa`).

4. Click **Apply**. The first build takes a few minutes.

> Service names decide the `.onrender.com` addresses. If a name is taken, Render adds a suffix — use the
> real addresses from the dashboard in `CORS_ORIGIN`, `WEB_APP_URL` and `VITE_API_URL`.
> `VITE_API_URL` is baked in at build time: after changing it, use **Manual Deploy → Clear build cache & deploy**.

## 3. Check
- `https://<api>/api/v1/health` → `"database": "connected"`
- `https://<api>/api/docs` → API documentation (share with the Android developer)
- School app opens the sign-in page; Platform Admin opens the dark *Platform sign in* page.

## 4. Create the real platform owner
The seed script refuses to run in production. From your own computer, pointing at the production database
(PowerShell):

```powershell
cd backend
$env:MONGODB_URI = "<production connection string>"
$env:MONGODB_DB_NAME = "school_prod"
npm run super-admin -- create --email you@company.com --name "Your Name"
Remove-Item Env:MONGODB_URI; Remove-Item Env:MONGODB_DB_NAME
```

Then sign in to the Platform Admin app, set up 2-step verification, and add the first school.

## 5. Custom domains (optional)
Render service → **Settings → Custom Domains** → add `api.yourdomain.com` (and `app.`, `admin.`), then create the
DNS records Render shows at your domain provider. Afterwards update `CORS_ORIGIN`, `WEB_APP_URL` and both
`VITE_API_URL` values, and redeploy the two web apps.

## 6. Good to know
| Topic | Note |
|---|---|
| Free plan | the API sleeps after ~15 minutes without traffic; the next request waits ~50 s. Use a paid instance for real schools. |
| Deploys | every push to `main` redeploys automatically (`autoDeploy: true`). |
| Logs | Render → service → **Logs**. Startup prints `✅ MongoDB connected` and `🚀 API running`. |
| Weak secrets | in production the API refuses to start with `change-me`-style or short JWT secrets. |
| Android app | uses the API address directly; CORS does not apply to mobile apps. |
| Rollback | Render → service → **Events** → redeploy an earlier deploy. |

## 7. Other hosts
The API is a normal Node app: `npm ci --include=dev && npm run build`, then `npm start` with the environment
variables above (Railway, a VPS with PM2 + Nginx, etc.). The web apps are static files (`npm run build` →
`dist/`) that any static host (Vercel, Netlify, Cloudflare Pages, Nginx) can serve; they use hash routing, so no
rewrite rules are needed.
